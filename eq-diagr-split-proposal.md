# Separating the calculations of SED and Predom from their windows

*Draft proposal for eq-diagr, branch `calc-split` (local, based on `master` at c94b0d8, not pushed). Two commits, also as patch files: `0001` separates SED and Predom from their windows, `0002` separates the database search from the DataBase window (see the last section). 2026-11-25.*

## Summary

SED and Predom are each a single `JFrame` class of 3,500 and 3,718 lines, in which reading the command line and the data file, the HaltaFall loop and the plot output are interleaved with widget updates. They therefore need a display even when they are run from the command line with `-d=file.dat -nostop`, and they cannot be used from other Java code, from a server without a display, or in a browser without copying their logic.

The branch moves the calculation path of each program into a new class without Swing or AWT, `simpleEquilibriumDiagrams.SedCalc` and `predominanceAreaDiagrams.PredomCalc`. `SED` and `Predom` keep the window, the events, the dialogs and the worker thread, and call the new classes for everything else. The moved methods are the original ones; what changed inside them is listed below. The plot files, table files and console output are identical to those of the current programs in all the cases I tested, with and without a window.

| File | `master` | `calc-split` |
|---|---|---|
| `SED.java` | 3,500 lines | 2,064 lines |
| `SedCalc.java` | | 1,669 lines (new) |
| `Predom.java` | 3,718 lines | 2,050 lines |
| `PredomCalc.java` | | 1,910 lines (new) |

`Plot`, `Table`, `Plot_Predom` and `Debugging` change only in the type of their first constructor parameter (`SedCalc` or `PredomCalc` instead of the frame), since they read the same fields as before. `initComponents()` and the variable declarations generated by NetBeans are unchanged, so the `.form` files still match; the frames keep `NSTP_MAX`, `NSTP_MIN` and `NSTP_DEF` as aliases because the generated code refers to them.

## How the two classes divide the work

`SedCalc` holds what used to be the calculation state of the frame (the chemical system, concentrations, options from the command line, the plot and table objects) and these methods, moved from `SED.java`: `dispatchArg`, `checkInput`, `readDataFile`, `showErrMsgBx`, `showMsg`, `set_tol_inComboBox` (now `set_tol`), `millisToShortDHMS` and `setPathDef`. The non-window half of `start` became `SedCalc.start(reversedConcs, args)`; `doCalculations` became `prepareCalculations()`, and the body of the `HaltaTask` SwingWorker became `calculate(progress)` (the loop of `doInBackground`) and `finishCalculations()` (the non-window part of `done`). `PredomCalc` is built the same way and also holds `findTopSpecies`, the `PredomData` instance and the area-limit bookkeeping of the 2-D loop.

The values that the calculations used to read back from widgets are now fields of the calculation class: the number of steps (`jScrollBarNbrPoints`), the text height (`jScrollBarHeight`), the activity-coefficient model (`jComboBoxModel`), the tolerance (`jComboBoxTol`), and the temperature and pressure that were kept as label text (`jLabelTemperature`, `jLabelPressure`). The window copies the scroll-bar and combo-box values into the calculation class just before calculating, as `doCalculations` read them at that point, and shows the values of the calculation class after the command line or a data file has been read (`showSettings()`). The ionic-strength text field and the check boxes already updated fields through their event handlers, which now write to `calc.ionicStrength`, `calc.calcActCoeffs` and so on.

What the calculations need from the window is a four-method interface, `SedCalc.Display` (and `PredomCalc.Display`), which the frames implement:

```java
void messageBox(String msg, int type);      // JOptionPane.showMessageDialog
boolean okCancelBox(String msg, int type);  // the OK/Cancel dialog of showErrMsgBxCancel
void dataFileRead(java.io.File dataFile);   // showTheInputFileName
void dataFileError();                       // the window part of readDataFile_hadError
```

Without a window the display is `null`, and messages go only to the `out` and `err` streams and to `System.out`/`System.err`, as before. Cancelling is `calc.cancel()`, which sets a volatile flag checked where the loop checked `finishedCalculations` and calls `h.haltaCancel()`. Progress is passed to an `IntConsumer`, which the window's `HaltaTask` forwards to `publish()`, so the progress label works as before.

## Running without a display

`SED.main` and `Predom.main` now check `GraphicsEnvironment.isHeadless()`. On a normal desktop nothing changes. With `java -Djava.awt.headless=true -jar SED.jar -d=file.dat ...`, or on a machine without a display, the program runs `SedCalc.run(args)` and writes the same plot and table files and the same console output as with the window, without opening one. It exits with status 1 if the plot file was not written, so scripts can test the result. Whether a command-line option such as `-nogui` would be preferable to the system property is for you to decide; I did not want to change the command line in this draft.

The same classes compile unchanged to JavaScript with TeaVM. The browser proof of concept in `webpoc/` (SED and Predom diagrams computed in the browser) previously had to generate headless copies of `SED.java` and `Predom.java` at build time; with this branch it compiles `SedCalc` and `PredomCalc` directly, behind two adapter classes of about 20 lines each.

## Verification

The comparisons are against the jars built from `master` with the same Java version, with the date line of the table files and the wall-clock time removed.

1. Seven SED inputs (phosphate and carbonate fraction and log-concentration diagrams, the H₃PO₄/NaOH titration, carbonate with Davies activity coefficients at *I* calculated, and with the simplified HKF model at *I* = 0.5 and 50 °C): `.plt` and `.csv` files byte-identical, with the window and headless; console output identical line by line.
2. Six Predom inputs (Fe Eh–pH diagrams with 60 and 150 steps, without haematite, with Davies activity coefficients, with `-aqu -ph -t=60`, and a log[Fe]–pH diagram): `.plt` files byte-identical, with the window and headless; console output identical.
3. Twelve edge cases for each program, together covering a malformed option, a truncated data file, a data file for the other program, SIT with a fixed ionic strength, `-tol=3e-6` and `-tol=1e-10`, `-h=1.57` and `-h=0.5`, `-dbg`, table and unit options, `-rev`, `-n=2`, `-i` without `-t`, and `-aqu -ph`: same files and messages. The only differences are stack-trace line numbers and, in headless debug runs, the window's own lines ("SwingWorker done.", "SED - finished.", the default path).
4. The windows driven through their widgets (a diagram from the command line with `-keep`, then changing the number of steps, the text height, the tolerance and the activity-coefficient settings and pressing "make the Diagram"): the same plot and table files as the original programs, and the same selected tab, status text and labels.
5. The browser build compiled from `SedCalc` and `PredomCalc`: byte-identical `.plt` and `.csv` files for the same seven SED and six Predom inputs.

## Behaviour kept on purpose

The split reproduces three behaviours of the current code exactly, although they look unintended. Each would be a one-line change in a separate commit, if you agree.

1. **Text height.** `doCalculations` sets `tHeight = jScrollBarHeight.getValue()/10`, an integer division, so the text-height factor is rounded down to a whole number: `-h=1.57` gives 1, and any value below 1 gives the minimum 0.3. `prepareCalculations` keeps this, with a comment.
2. **Tolerance.** Selecting an item of `jComboBoxTol` from `set_tol_inComboBox` fires its action listener, which sets `tolHalta = 0.01/10^index`. A tolerance given with `-tol=` is therefore replaced by the nearest power of ten (`-tol=3e-6` is reported and used as 1.0E-6). `set_tol()` now does this explicitly, so the calculation class behaves the same with or without a window.
3. **Activity-coefficient model after an error.** If `new Factor(...)` throws in `doCalculations`, `factor` keeps the instance from the previous diagram, so the check `factor == null` does not stop the calculation in a session where a diagram has already been made. This only matters in the window, after a failed second diagram.

## Open points

The class names (`SedCalc`, `PredomCalc`) and the place of the `Display` interface are suggestions. The calculation fields that the window needs are package-private, following the existing style in which `Plot` and `Table` read the frame's fields; a stricter version would add getters and setters. No code outside the two packages refers to the frames, Spana included, so nothing else needs to change.

## Second patch: the database search

The same approach applied to DataBase. `DBSearch` already held the search, but it read the selected components, the progress bar and a label from `FrameDBmain`, showed three message boxes itself, and took its options from `ProgramConf` and `ProgramDataDB`. In the second patch it uses neither Swing nor AWT:

1. The search takes the list of selected components and a `DBSearch.Display` (progress label, progress bar, the "solids excluded" label, and a Continue/Cancel question for the two warnings that the search can raise). `FrameDBmain` implements it with the same widgets and dialogs as before. Without a display the search runs silently and goes on after warnings.
2. The options of the AskRedox and AskSolids dialogs (redox for N, S and P; which solids to exclude) are fields of `DBSearch`, which `FrameDBmain` sets from `ProgramDataDB` before each search.
3. Four pieces of work that were done inside dialogs are now methods without dialogs: `checkTemperature()` returns the species without temperature-pressure data (`FrameDBmain.checkTemperature` shows the same message box as before), `componentPosition` gives the order of the selected components (H⁺ first, e⁻ next, solids last; used by `availableComponentClick`), `includeWater` adds H₂O, and `writeDataFile` writes the chemical system (used by `ExitDialog`, which keeps the file chooser and the temporary file).
4. In `LibDB`, the static `screenSize` field called `Toolkit.getScreenSize()` when the class was loaded, so the database library could not be used without a display; it moved to the two windows that use it. `LibDB.readElements` reads the element files of a list of databases and reports problems as exceptions instead of message boxes.

For the comparison, a test harness drove the original and the new DataBase window through the same steps as a user (element buttons and component lists, Search and Exit, Save with its file chooser, answering the message boxes). Twenty searches cover the five databases of the release (`Reactions.db`, `Medusa-Hydra.db`, `MintEQ-v4.db`, `Wateq4F.db`, and the text database `Soltherm.txt`) and two of them together, redox systems with and without N, S and P redox, the three solid exclusions, 25 to 250 °C, H₂O as a component, components chosen in different orders, and the warning for Fe²⁺ with Fe³⁺. Nineteen searches write a data file, and the files are identical between the original and the new window and when written with the new methods without a display (`java.awt.headless=true`); the twentieth (CaCO₃ at 200 °C) stops in all versions because CaCO₃(am) has no data above 100 °C. No database in the release has solid components, so that branch of `componentPosition` is not covered by these tests.

With this patch the database search also runs in the browser (TeaVM), where it gives the same nineteen files. Since the thermodynamic databases are not in the repository, the browser page offers the small sample `DataMaintenance/Reactions.db` from the repository and lets users load full database files from their own computer; whether the release databases may be served from a website is for you to decide.
